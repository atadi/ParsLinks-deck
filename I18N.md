# Internationalization (i18n) Architecture

Locale is a **first-class routing and rendering concern**, implemented with
[next-intl](https://next-intl.dev) on top of the App Router.

## Stack

- **next-intl v4** (`next-intl`, `next-intl/server`, `next-intl/navigation`)
- Routing strategy: `localePrefix: "always"` — every URL carries the locale
  (`/fa`, `/en`, `/fa/main/3`, `/en/technical`).
- **Static export** (`output: "export"`): there is **no server middleware**.
  Locale auto-detection for the bare root `/` happens client-side (see below).

## Locale registry

Single source of truth: `src/i18n/config.ts`

```ts
export const locales = ["fa", "en"] as const
export type Locale = (typeof locales)[number]
export const defaultLocale: Locale = "fa"

export const localeMeta: Record<Locale, { dir: "rtl" | "ltr"; label: string }> = {
  fa: { dir: "rtl", label: "فارسی" },
  en: { dir: "ltr", label: "English" },
}
```

Adding a language = one line in `locales` + a UI message catalog
(`src/content/messages/<locale>.json`) + populate every presentation content id
in `src/content/presentation.json`. The type system (`Locale`) propagates the
requirement everywhere; nothing hardcodes `fa`/`en`.

## Route structure

```
src/app/
  layout.tsx              # passthrough root (Next requires a root layout boundary)
  page.tsx                # "/"  -> client redirect to default/remembered locale
  main/page.tsx           # "/main"  -> redirect to "/fa/main"  (back-compat)
  technical/page.tsx      # "/technical" -> redirect to "/fa/technical" (back-compat)
  [locale]/
    layout.tsx            # owns <html lang dir>, NextIntlClientProvider, Providers, EditMode
    page.tsx              # Landing (cover)
    main/page.tsx         # Main deck (/[locale]/main)
    technical/page.tsx    # Technical Deep Dive (/[locale]/technical)
```

Backward compatibility: old unprefixed routes (`/main/3`, `/technical/2`) are
redirected to the default-locale equivalent (`/fa/main/3`). The remembered
locale (from the language switcher) is used for the bare `/` redirect.

## Direction (RTL/LTR)

`dir` derives from `localeMeta[locale].dir` and is set **server-side** in
`[locale]/layout.tsx` (`<html lang={locale} dir={dir}>`), so there is no
hydration language/direction switch. All layout uses logical CSS
(`margin-inline`, `inset-inline`, `text-align: start`) so the same components
mirror correctly in RTL and LTR.

## Content vs. UI strings (the key separation)

| Concern | Lives in | Example |
|---|---|---|
| Audience-visible **presentation copy** (editable) | `src/content/presentation.json` (canonical) + localStorage overrides | slide headlines, subtitles, CTA |
| **Application / chrome UI** strings | `src/content/messages/<locale>.json` (next-intl) | Edit, Save, Cancel, Previous, Next, Overview, Help |

Presentation copy stays in `presentation.json` so Edit Mode (`?edit=1`),
content export/import, and `content:apply` keep working unchanged. Chrome
strings moved to next-intl so they are locale-scalable and not scattered as
`lang === "fa" ? … : …` ternaries.

### Accessing strings

- **Presentation copy**: the `CT` primitive in `src/content/edit.tsx`
  (`<CT k="hero.title" />`) resolves the active-locale value from the canonical
  JSON + localStorage overrides.
- **UI strings**: `useTranslations("ui")` from next-intl (see `EditToolbar`,
  `Deck` HUD).

## Locale-generic Edit Mode

- The editor renders **one field per registered locale** (mapped from
  `locales`), not hardcoded fa/en. Adding a locale automatically adds an editor
  field.
- Override storage is locale-generic: keyed by `Locale`, schema `v2`.
- **Migration**: legacy v1 overrides (`{fa, en}` shape) are migrated to v2 on
  first read and re-persisted — user edits are never lost.

## Import / export

`Export` downloads an overrides file of shape:

```json
{ "schemaVersion": 2, "locales": ["fa", "en"], "overrides": { "<id>": { "fa": "…", "en": "…" } } }
```

`scripts/content-apply.mjs` accepts **schema 1 or 2**, validates every locale
value, and writes atomically. Unknown locales / content ids are reported and
skipped.

## Content validation

```bash
pnpm run content:validate
```

Reports any content id missing a value for any supported locale. Run before a
presentation or in CI.

## Locale switcher

`useLang().toggle()` (in `Providers`) swaps the first path segment
(`/fa/…` ↔ `/en/…`) while preserving the rest of the path, the slide hash
(`#n`), and all query params (notably `edit=1`). Priority: **URL locale >
remembered cookie > default locale**.

## Adding a new language (checklist)

1. Add the code to `locales` in `src/i18n/config.ts` and a `localeMeta` entry.
2. Create `src/content/messages/<code>.json` with the `ui`/`validation` keys.
3. Populate every id in `src/content/presentation.json` for the new locale.
4. `pnpm run content:validate` must pass.
5. QA direction/layout in the new locale.

No component, route, or helper needs restructuring — the registry drives it.
